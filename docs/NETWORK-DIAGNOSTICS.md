# ТЗ: сетевая диагностика shoulderkop

Статус: **реализовано в 0.4.2** (v1, см. §11 «Принятые решения»). Документ описывает,
что именно делает диагностика и почему так.

## 1. Зачем

Сейчас shoulderkop умеет обновлять подписку и раскладывать секции podkop, но не проверяет,
что получившийся туннель действительно работает. Из-за этого типовые поломки замечает
только человек, у которого уже пропал интернет:

1. **podkop падает** (в том числе при `urltest`-секции, когда ни один сервер не отвечает) —
   вместе с ним пропадает интернет на всём LAN.
2. **Снимается автозапуск** podkop/sing-box (последствия падения или паузы подписки) —
   после перезагрузки туннель не поднимается, и это никто не видит.
3. **Провайдер рубит DoH/DoT** — podkop не может поднять DNS, секции не работают.
   Лечится переходом на UDP + 77.88.8.8, но вручную и не сразу.
4. **Нет живых серверов** — `urltest` не может выбрать узел, podkop висит «мёртвым»
   и тянет за собой DNS/маршруты.

Нужен демон, который периодически проверяет сеть, при поломке — пытается починить, и
показывает состояние в LuCI.

## 2. Что уже есть (на что опираемся)

* `lifecycle.uc` — пауза/возврат туннеля, снимок состояния сервисов, снятие и возврат
  автозапуска (`suspend()` / `resume()` / `service_state()`).
* `apply.uc` — знает про секции podkop, режимы, списки, `engine_decode_link`.
* `main.uc` — `shoulderkop update` (fetch → parse → apply → reload podkop), cron-расписание,
  `status` в JSON.
* Установщик умеет ставить/обновлять podkop и sing-box.

Диагностика должна переиспользовать это, а не дублировать: проверки — новый модуль
`diag.uc`, ремонт — вызовы `lifecycle.resume()`, `podkop restart`, правка DNS-настроек.

## 3. Архитектура

```
procd service  →  shoulderkop diag run          (короткий запуск, без демона-цикла)
cron/lock      →  каждые N минут лёгкая проверка
                 ├─ ok        → выход, ничего не пишем в журнал (кроме --verbose)
                 └─ fail      → полная проверка + repair (с лимитами)
```

* **Не отдельный процесс-цикл**, а запуск по расписанию (procd `respawn` не нужен):
  меньше памяти на 454 МБ роутере, нечему «зависать». Триггеры: cron, `ifup` (hotplug
  wan), `podkop` restart, ручная кнопка в LuCI.
* **Лёгкая проверка** (дёшево, без сети наружу): процесс sing-box, nft-таблица
  `PodkopTable`, автозапуск podkop, `default route`, резолв `dnsmasq`.
* **Полная проверка** запускается только если лёгкая провалилась или прошло больше
  `diag_full_interval` (по умолчанию час): внешние запросы, DNS-апстримы, узлы, туннель.
* **Ремонт** — только по конкретным правилам (см. §5), с лимитом попыток и cooldown,
  чтобы не устраивать шторм перезапусков.
* **Lock**: `flock /var/lock/shoulderkop-diag.lock` — демон и `shoulderkop update`
  не должны работать одновременно (обновление подписки само дергает podkop).

## 4. Проверки

| # | Проверка | Как | Критерий «плохо» |
| --- | --- | --- | --- |
| 1 | `wan` | `ip route show default`, `ping -c1 -W2` шлюз | нет маршрута / шлюз не отвечает |
| 2 | `dnsmasq` | `pgrep dnsmasq`, `nslookup openwrt.org 127.0.0.1` | процесс мёртв / не резолвит |
| 3 | `podkop-enable` | `/etc/rc.d/S*podkop` | симлинка нет |
| 4 | `singbox` | `pgrep -f '[s]ing-box[^ ]* run'` + `pidof sing-box-core` | процесса нет |
| 5 | `nft` | `nft list table inet PodkopTable` | таблицы нет при включённом podkop |
| 6 | `urltest` | Clash API `192.168.1.1:9090` → `/proxies` (если API включён) | нет выбранного узла / все `delay=0` |
| 7 | `dns-upstream` | DoH: `curl -m5 -s https://dns.google/resolve?name=openwrt.org`; DoT: `curl -m5 --doh-url` не подходит → `nc -z -w3 8.8.8.8 853` + `kdig`/`drill` если есть; UDP: `nslookup openwrt.org 77.88.8.8` | таймаут/ошибка TLS |
| 8 | `tunnel-http` | HTTP 204 через прокси-интерфейс: `curl -m8 -x socks5h://127.0.0.1:<mixed-in> https://www.google.com/generate_204` (порт берём из конфига podkop) | не 204 / таймаут |
| 9 | `direct-http` | `curl -m8 https://www.google.com/generate_204` без прокси | таймаут (общий провал WAN) |
| 10 | `subscription` | `shoulderkop status` → `count`, `status: expired` | `count=0` при живых узлах / `expired` |

Проверки 1–5 — «лёгкие», 6–10 — «полные».

## 5. Правила ремонта

| Симптом | Действие | Ограничение |
| --- | --- | --- |
| нет `S*podkop`, но podkop установлен | `podkop enable && podkop start` | 1 раз за проверку |
| sing-box не запущен, podkop включён | `podkop restart` | не чаще 3 раз / 30 мин, потом только уведомление |
| нет `PodkopTable` при работающем sing-box | `podkop restart` | как выше |
| DoH/DoT не отвечают, UDP отвечает | переключить DNS podkop на UDP `77.88.8.8` (см. §6) | 1 переключение / 6 ч |
| все узлы `delay=0`, секция `urltest` | НЕ снимать автозапуск; переключить секцию на следующего кандидата / оставить direct DNS | уточнить (§7, вопрос 7) |
| `wan` мёртв | ничего не чиним (это не наша зона), пишем в статус | — |

После ремонта — повторная лёгкая проверка через 10–20 с; результат пишем в журнал
(`logread -e shoulderkop-diag`) и в `status.diag`.

## 6. DNS: лестница приоритетов

Требование: приоритет от лучшего варианта к худшему, при блокировке — спуск на ступень ниже.

```
1. 8.8.8.8        DoT  (:853) — лучший вариант из рабочих, сертификат с IP-SAN
2. 1.1.1.1        DoH  (https://1.1.1.1/dns-query)
3. 1.1.1.1        DoT  (:853)
4. 77.88.8.8      DoT  (:853)
5. 77.88.8.8      UDP  (:53) — последний рубеж, работает почти всегда
```

Только IP, без имён: когда DNS сломан, резолвить `dns.google` нечем, а bootstrap
сам может не работать. Проверено на живом роутере:

| Ступень | Результат |
| --- | --- |
| `https://1.1.1.1/dns-query` | 200 (Cloudflare, cert с IP-SAN) |
| `dig @8.8.8.8 +tls` / `@1.1.1.1` / `@77.88.8.8` | ok (все три сертификата с IP-SAN) |
| `dig @77.88.8.8` (UDP) | ok |
| `https://8.8.8.8/dns-query` | 400 — Google требует SNI/Host `dns.google`, podkop задаёт только адрес |
| `https://77.88.8.8/dns-query` | 404 — у Яндекса DoH по IP не поднят |

Поэтому Google в лестнице остаётся только DoT, DoH — один (Cloudflare), а Яндекс —
DoT + UDP. Если у провайдера когда-нибудь заработает ещё какой-то DoH по IP, ступень
добавляется одной строкой в `LADDER` (`diag.uc`).

* Проверка ступени: резолв `openwrt.org` через конкретный сервер (DoH — HTTPS-запрос,
  DoT — TLS-хендшейк + DNS-запрос; UDP — обычный `nslookup`).
* Спуск: как только ступень не отвечает 2 проверки подряд (по умолчанию 2 × 5 мин),
  переключаем podkop на следующую и **запоминаем** в uci (`dns_level`).
* Возврат наверх: раз в `dns_retry_interval` (по умолчанию 1 ч) пробуем ступени выше
  текущей; если заработала — возвращаемся.
* Реализация записи в podkop: `podkop.settings.dns_type` + `dns_server` (у podkop
  это `doh`/`dot`/`udp` и адрес в `dns_server`) — точные имена опций уточнить
  по установленной версии (§7, вопрос 6).
* Всё логируем: `dns_level=3 (1.1.1.1 DoH) → fail → 4 (1.1.1.1 DoT)`.

## 7. Настройки (uci `shoulderkop.settings`)

| Опция | По умолчанию | Смысл |
| --- | --- | --- |
| `diag_enabled` | `1` | включить диагностику |
| `diag_interval` | `5m` | период лёгкой проверки |
| `diag_full_interval` | `1h` | как часто разрешать полную проверку |
| `diag_repair` | `1` | разрешить автоматический ремонт |
| `dns_level` | `0` | текущая ступень DNS (0 — авто с 1-й) |
| `dns_retry_interval` | `1h` | как часто пробовать вернуться наверх |

## 8. Интерфейс и статус

* `shoulderkop diag` — прогнать сейчас, печать отчёта по-человечески.
* `shoulderkop diag --json` — машинный отчёт (для LuCI).
* `shoulderkop status` — добавляем блок `diag: { ts, ok, failed: [...], repairs: [...] }`.
* LuCI: блок «Диагностика» — время последней проверки, галочки/крестики по пунктам,
  кнопка «Проверить сейчас», поле интервала (только если `diag_enabled`).
* Cron-строка отдельная от обновления подписки, чтобы не блокировать друг друга
  дольше, чем на время lock.

## 9. Границы

* Не перезагружаем роутер и не трогаем `network`/`firewall` конфиг.
* Не удаляем секции `skop_*` и не меняем режим.
* Не отправляем ничего наружу (никакой телеметрии).
* Все внешние проверки — с таймаутом 5–8 с и общим бюджетом ~25 с на полную проверку.
* Совместимость: apk (25.x) и opkg (24.10), busybox-утилиты; `curl` уже зависимость.

## 10. Вопросы (нужны ответы до реализации)

1. **Демон**: делаем сервис внутри пакета `shoulderkop` (`/etc/init.d/shoulderkop-diag`)
   или отдельным пакетом? Предлагаю внутри.
2. **Интервалы**: лёгкая 5 мин, полная 1 ч — ок? Или реже (10 мин / 3 ч)?
3. **Что считать «интернет пропал»**: `ping` до шлюза + `curl` HTTP 204 напрямую? Или
   достаточно `ping 77.88.8.8`?
4. **Ремонт**: разрешаем автоматически перезапускать podkop (до 3 раз / 30 мин)?
   Или только уведомлять, а перезапуск — по кнопке в LuCI?
5. **Возврат наверх по DNS**: нужно ли автоматически возвращаться на DoH, когда
   провайдер «отпустил» (раз в час), или оставаться на UDP до ручного вмешательства?
6. **Точные DoH/DoT-хосты для Яндекс-ступени** (5) и **имена опций podkop** для DNS
   (`dns_type`/`dns_server`?) — подтвердить на текущей версии podkop 0.7.24.
7. **Нет живых узлов**: что правильнее — оставить podkop включённым и ждать, пока
   подписка обновится, или временно переводить секцию в `selector`/`direct`? Сейчас
   podkop в такой ситуации роняет интернет.
8. **Снятие автозапуска**: если нашли `podkop` без `S`-симлинка — включать обратно
   автоматически или спрашивать в LuCI (баннер «автозапуск был выключен, вернуть?»)?
9. **Уведомления**: достаточно LuCI + `logread`, или нужен ещё внешний канал
   (Telegram-бот/почта) — если да, то какой и с какими токенами?
10. **История**: хранить последние N результатов в `/tmp` (переживает только до
    перезагрузки) или писать в `/etc/shoulderkop/diag.log` (износ flash)?
11. **Ручной запуск**: нужна ли кнопка «Проверить сейчас» в LuCI, или достаточно CLI?
12. **Hotplug**: дёргать проверку на `ifup wan` (полезно для LTE, где WAN
    переподключается часто) — включаем?


## 11. Принятые решения

| № | Вопрос | Решение |
| --- | --- | --- |
| 1 | Демон отдельным пакетом? | Нет: модуль `diag.uc` + команда `shoulderkop diag` внутри пакета `shoulderkop`, запуск по cron (без своего процесса-цикла) |
| 2, 3 | Интервал и признак «работает» | Каждые 5 минут; критерий — HTTP-запрос на `https://www.gstatic.com/generate_204` (как `urltest_testing_url` у podkop). 200/204/301/302 = сеть в порядке |
| 4 | Автоматический ремонт | Да, перезапуск podkop во время починки (лимит: 3 раза / 30 минут, затем только запись в лог) |
| 5 | Возврат с UDP на DoH | Остаёмся на UDP `77.88.8.8`, если это единственная рабочая ступень; подъём наверх — только если ступень выше реально отвечает (проверяется при следующей полной проверке) |
| 6 | DoH/DoT-хосты, опции podkop | Опции podkop: `dns_type` (`doh`/`dot`/`udp`) и `dns_server` — проверено по исходникам podkop 0.7.24. Ступени заданы **только IP**: `8.8.8.8` DoT, `1.1.1.1` DoH, `1.1.1.1` DoT, `77.88.8.8` DoT, `77.88.8.8` UDP. Google DoH и Яндекс DoH по IP не работают (400 и 404), поэтому их в лестнице нет |
| 7 | Все узлы мертвы | Переводим всё в direct: `podkop disable && stop`, снимаем nft-таблицу, `direct_mode=1`. Возврат — после успешного обновления подписки (`cmd_update` вызывает `diag.after_update()`) |
| 8 | Снятый автозапуск podkop | Возвращаем автоматически (`podkop enable`) — это часть починки. Баннер не показываем |
| 9 | Уведомления | Только `logread -e shoulderkop-diag` (+ блок в LuCI), внешних каналов нет |
| 10 | История | `/tmp/shoulderkop.diag.history.json`, не больше 10 последних значимых проверок (успешные тихие проверки не пишутся) |
| 11 | Кнопка в LuCI | Да: блок «Диагностика» со статусом, списком проверок, действиями починки и кнопкой «Проверить сейчас» |
| 12 | Hotplug | Да: `/etc/hotplug.d/iface/99-shoulderkop` на `ifup wan|wwan*` запускает `shoulderkop diag --quick --quiet` (без починки, чтобы не дёргать podkop на каждый ifup) |

### Как это работает в коде

* `shoulderkop diag` — полный проход; `--quick` — только gstatic; `--quiet` — для cron;
  `--json` — для LuCI; `--force` — игнорировать `diag_enabled`.
* cron: отдельная строка от обновления подписки (`*/5 * * * * /usr/bin/shoulderkop diag --quiet`,
  интервал берётся из `diag_interval`).
* Ремонт по шагам: включить автозапуск → перезапустить podkop (если sing-box/nft мертвы) →
  спуститься по DNS-лестнице до первой отвечающей ступени → при отсутствии интернета перевести
  в direct. После каждого шага — повторная проверка gstatic.
* Всё пишется в лог только при проблемах или починке.
